Installing a C/C++ Compiler on Windows 11

August 2026 · Windows · Toolchains · C / C++ · ~15 min read

Windows operating systems do not natively ship with a C or C++ compiler like Linux or macOS, which often makes the very first step of "learning C/C++" the hardest one for Windows users. This blogpost walks through getting a complete GCC toolchain running on a clean Windows 11 install, from download to a compiled executable, and then covers the two alternatives worth knowing about: Microsoft's own MSVC, and the Linux toolchain via WSL.

01Choosing a toolchain

There are three realistic ways to compile C and C++ on Windows 11, and they are not interchangeable. Picking one on purpose now saves a lot of confusion later, because binaries and libraries built by one toolchain generally will not link against another.

Toolchain Compilers Best for
MinGW-w64 via MSYS2 gcc, g++, gdb Native Windows .exe files, coursework, portable code that also builds on Linux. This is the setup I use.
MSVC Build Tools cl.exe, link.exe Windows API and COM work, Visual Studio projects, anything consuming a library shipped as an MSVC .lib.
WSL 2 gcc, g++, clang Code that targets Linux servers, or systems work that needs real POSIX behaviour rather than an emulation of it.

The main path below installs MinGW-w64 through MSYS2. It gives you a current GCC, the GDB debugger, and a package manager to keep them updated, and it produces ordinary Windows executables that you can hand to someone else and expect to run. Sections 10 and 11 cover the other two if you need them.

Why not the old MinGW installer?

The original mingw.org distribution has not shipped a modern GCC in years and only targets 32-bit. MinGW-w64 is the maintained fork, and MSYS2 is the most reliable way to get it. If you already have an old MinGW on this machine, uninstall it and strip it out of PATH before continuing; two GCCs on one PATH is the single most common source of "it compiled yesterday" bugs.

02Before you start

  • Windows 11, 64-bit. Everything here also works on Windows 10 22H2.
  • An account that can install software. You do not need to run the terminal as administrator for any step except the installer itself.
  • Roughly 3 GB of free disk space for MSYS2 plus the toolchain.
  • A working internet connection; the toolchain is downloaded from mirrors during install.

One note on terminals, since this trips people up constantly. MSYS2 installs several Start menu entries that all look like the same terminal: MSYS2 MSYS, MSYS2 UCRT64, MSYS2 MINGW64, and others. They are different environments with different PATHs and different package prefixes. Which one you open matters. I will be explicit each time.

03Install MSYS2

Download the installer from msys2.org and run it. Accept the default install location, C:\msys64. Paths with spaces in them cause avoidable grief with build tools, so if you do move it, keep it somewhere short and space-free like C:\dev\msys64.

Either way, when it finishes, open the Start menu and launch MSYS2 UCRT64. The prompt should show UCRT64 in it. If it says MSYS instead, you have the wrong terminal open; close it and launch the UCRT64 one.

UCRT64 vs MINGW64

UCRT64 links against Microsoft's Universal C Runtime, which has shipped with Windows since Windows 10 and handles Unicode and locales correctly. MINGW64 links against the ancient msvcrt.dll. Both work, but UCRT is the current recommendation and what you want on Windows 11. Just be consistent: do not install half your libraries from one environment and half from the other.

06Add the compiler to PATH

At this point g++ works inside the MSYS2 terminal but nowhere else. To use it from PowerShell, Command Prompt, or VS Code, Windows needs to know where it lives. The directory is:

To add it:

  1. Press Win + R, type sysdm.cpl, press Enter.
  2. Go to the Advanced tab, then click Environment Variables.
  3. Under User variables, select Path and click Edit.
  4. Click New, paste C:\msys64\ucrt64\bin, and click OK on all three dialogs.
Add only that one directory

Do not add C:\msys64\usr\bin to your Windows PATH. It contains MSYS versions of common Unix utilities that will shadow Windows commands and confuse other tools. The ucrt64\bin directory alone is what you want.

PATH changes only apply to newly opened terminals. Close every PowerShell window you have open, along with VS Code if it is running, before testing.

Flags worth knowing from day one

  • -Wall -Wextra -Wpedantic — turn on the warnings that catch real bugs. Enable them from the start and treat them as errors you have not gotten around to yet.
  • -std=c++17 / -std=c17 — pin the language standard explicitly so your build does not silently change when GCC updates its default.
  • -g -O0 — a debug build: full symbols, no optimisation. Use this whenever you plan to step through code in GDB.
  • -O2 -DNDEBUG — a release build: optimised, assertions compiled out.

Ctrl + Shift + B now builds the file you have open, and compiler errors become clickable entries in the Problems panel. For debugging, add a launch configuration with "type": "cppdbg" and "miDebuggerPath": "C:/msys64/ucrt64/bin/gdb.exe".

Forward slashes in those paths are deliberate. JSON treats a backslash as an escape character, so C:\msys64 either errors or silently becomes something you did not intend.

10Alternative: MSVC Build Tools

If you are writing against the Win32 API, consuming a library distributed as an MSVC .lib, or working in a codebase that already targets Visual Studio, use Microsoft's compiler instead. You do not need the full Visual Studio IDE for this.

  1. Download Build Tools for Visual Studio from Microsoft's downloads page, under "Tools for Visual Studio".
  2. In the installer, check the Desktop development with C++ workload and install.
  3. Open Developer PowerShell for VS from the Start menu, not a plain terminal.

MSVC deliberately does not add itself to your global PATH, because it needs a pile of environment variables set to find its headers and libraries. That is what the developer prompt does for you. Running cl from an ordinary terminal will fail even when the install is perfectly fine.

12Troubleshooting

"g++ is not recognized as the name of a cmdlet"

PATH is not being picked up. Almost always this is one of three things: the entry was added to a dialog that got cancelled, the terminal was open before the change was made, or the path has a typo. Confirm what Windows actually has:

The wrong compiler runs

where.exe g++ printing several lines means something else is shipping a GCC — Strawberry Perl, Git for Windows, Chocolatey's mingw package, and various IDE bundles all do. Either uninstall the extra one or move C:\msys64\ucrt64\bin above it in the PATH editor, and reopen the terminal.

The program built but exits instantly with no output

Double-clicking a console .exe in Explorer opens a window, runs the program, and closes the window the moment main returns. Nothing is wrong. Run it from a terminal instead, which is where console programs are meant to be run.

Windows Defender quarantines your executable

Freshly compiled, unsigned binaries occasionally trip heuristic detection. It is a false positive. Adding your projects directory as an exclusion in Windows Security stops it — do this for a directory you control, and not for anything broad like your whole user profile.

Undefined references when linking a library

If the library was built with MSVC and you are linking with GCC (or the reverse), it will not work; the two use incompatible ABIs and name mangling. Get a build of the library for your toolchain, ideally from pacman: pacman -Ss ucrt-x86_64-<library>.

Where to go from here

Once g++ hello.cpp works, the next things worth learning, roughly in order: a build system so you stop typing compiler flags by hand (CMake with Ninja, both installed in step 05), then GDB properly, then a sanitiser pass with -fsanitize=address,undefined on your debug builds, which will find memory bugs far earlier than reading the code again will.
